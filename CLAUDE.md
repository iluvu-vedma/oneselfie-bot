# CLAUDE.md

Инструкции для Claude Code в этом репозитории. Читай целиком перед первой правкой в сессии.

## Что это за проект

Телеграм-бот на **grammY** (TypeScript). Продаем обертку к nano banana.

Основная ценность проекта — не код, а **интерфейс**. Бот состоит из экранов, и качество экранов важнее элегантности абстракций. Когда правишь текст или клавиатуру — ты правишь продукт, а не строку в файле.


# Модель навигации: один экран — одно сообщение

Нажатие кнопки **редактирует то самое сообщение, на котором стоит клавиатура**. Новое сообщение не отправляется. Чат не растёт, юзер смотрит в одну точку.

Новое сообщение отправляется только когда нужен **отдельный объект в ленте**: результат генерации, чек об оплате, подарок при старте, входящее уведомление. Всё остальное — редактирование.

## Как это делается в grammY

Есть два подхода. **Выбери один на весь проект и не смешивай.**

**A. Плагин `@grammyjs/menu`** — если структура меню в основном статична.

```ts
const payment = new Menu<MyContext>("payment")
  .text({ text: "СБП", style: "success" }, (ctx) => ctx.menu.nav("payment-sbp")).row()
  .back("⊗ Назад");

const main = new Menu<MyContext>("main").submenu("Пополнить баланс", "payment");
main.register(payment);          // после register достаточно bot.use(main)
bot.use(main);
```

Что он берёт на себя: перерисовку сообщения, стек «назад» (`ctx.menu.back()`, `ctx.menu.nav()`, `ctx.menu.update()`), автоматический `answerCallbackQuery` (отключается через `autoAnswer: false`) и детект устаревшего меню — если юзер нажал кнопку на старом сообщении далеко вверху чата, обработчик не запускается, сообщение перерисовывается свежим меню (`onMenuOutdated`). Задай в `onMenuOutdated` человеческий текст на русском, дефолт английский.

**B. Ручной роутер экранов** — если экраны сильно динамические (списки, пагинация, состояние из БД).

```ts
// screens/payment-stars.ts
export function render(ctx: MyContext): { text: string; reply_markup: InlineKeyboard } { ... }

bot.callbackQuery(/^nav:(.+)$/, async (ctx) => {
  const screen = screens[ctx.match[1]];
  await ctx.answerCallbackQuery();
  const { text, reply_markup } = screen.render(ctx);
  await ctx.editMessageText(text, { parse_mode: "HTML", reply_markup });
});
```

При этом подходе каждый экран — чистая функция от состояния к `{ text, reply_markup }`. Никакого «дописать строчку сверху»: экран всегда отрисовывается целиком.

## Обязательные детали

- **`answerCallbackQuery` вызывается всегда**, даже пустой — иначе на кнопке крутятся часики. Плагин menu делает это сам, ручной роутер — нет.
- **Мелкие отклики — тостом, не экраном.** «Скопировано», «Пока недоступно», «Недостаточно средств» → `ctx.answerCallbackQuery({ text, show_alert: true })`.
- **`message is not modified`** — штатная ситуация, а не падение. Лови `GrammyError` с этим описанием в `bot.catch` и глотай молча.
- **Долгие операции.** Сразу перерисуй экран в состояние «идёт работа», потом в результат. Тишина после нажатия — баг. Для генерации >10 сек добавь `ctx.replyWithChatAction`.
- **Двойное нажатие не ломает состояние.** Операция идемпотентна, либо кнопка после нажатия исчезает из перерисованного экрана.
- **`callback_data` ≤ 64 байта.** Только латиница и цифры — кириллица занимает 2 байта на символ. Схема: `домен:действие:параметр` (`pay:stars:100`). Не клади в callback ничего, что можно достать из сессии.
- **Ошибки не всплывают наружу.** `bot.catch` разделяет `GrammyError` (Telegram отказал), `HttpError` (сеть) и всё остальное; юзеру показывается человеческий текст, в лог уходит стек.

## Ограничения API, которые ломают архитектуру

- `editMessageText` работает **только для текстовых сообщений**. У сообщения с фото текст живёт в `caption` → `editMessageCaption` / `editMessageMedia`.
- **Превратить текстовое сообщение в медийное и обратно нельзя.** Один поток экранов — либо весь текстовый, либо весь медийный. Это решается при проектировании, а не патчится потом.
- Лимиты: текст 4096 символов, подпись 1024.
- `parse_mode: "HTML"` везде. MarkdownV2 не используем: в нём 18 символов требуют экранирования, и на пользовательских данных это стабильный источник багов. Пользовательский ввод в тексте всегда прогоняй через escape-хелпер.

# Дизайн-система экранов

## Анатомия экрана

Порядок жёсткий:

```
[иконка] <b>Заголовок</b>                 ← 2–4 слова, называет место, где юзер находится

Одна строка сути или ключевой факт        ← курс, баланс, цена, что тут произойдёт

[иконка] <b>Блок</b>                      ← если на экране несколько сущностей
Одна-две строки о нём.

[иконка] <b>Блок</b>
Одна-две строки о нём.

<i>Снятие возражения, если оно тут есть</i>

Выбирай кнопку ниже ⌄                     ← мостик к клавиатуре
```

Правила:

- **Мостик обязателен.** Последняя строка заканчивается `⌄`, стрелка физически указывает на клавиатуру и склеивает текст с кнопками в один объект.
- **Ключевой факт повторяется на каждом экране воронки.** Курс «1 Персона = 1 ₽» стоит и на главном экране, и на выборе способа оплаты, и на выборе суммы. Юзер не должен ничего помнить.
- **Оффер не теряется.** Действующая акция дублируется на каждом шаге до оплаты, а не только на входе.
- **Возражение снимается там, где возникает**, а не в разделе помощи. Экран оплаты звёздами → прямо на нём курсивом, где взять звёзды.
- **Абстрактная валюта переводится в результат.** Не «500 звёзд», а `500 ⭐ · ≈ 25 кадров`. Юзер думает кадрами, а не токенами.
- **Персонализация только в приветствии.** Имя в `/start` — уместно, имя на каждом экране — навязчиво.
- **Пустая строка — единственный инструмент вертикального ритма.** Никаких `---`, `###`, `• ` списков, линеек из символов. Markdown в тексте сообщения Telegram не рендерит, юзер увидит символы.
- **Длинную справку прячь в `<blockquote expandable>`**, а не выноси в отдельный экран.

## Клавиатуры

- **Максимум 8 кнопок на экран.** Больше — экран надо разбить.
- **Ряды несут смысл.** Одна кнопка в ряду = важное самостоятельное действие. Две = равнозначные второстепенные. Три+ — только для коротких лейблов.
- **Текст кнопки ≤ 30 символов**, иначе на мобиле переносится и ряд разъезжается. Глагол в повелительном: «Создать изображение», не «Создание изображений».
- **Цвет — сигнал, а не украшение.** Поле `style` у `InlineKeyboardButton`, три значения (Bot API 9.4):
  - `primary` (синий) — главное действие экрана. Один-два на экран, не больше.
  - `success` (зелёный) — деньги и подтверждения: пополнить, оплатить, подтвердить заказ.
  - `danger` (красный) — необратимое: удалить, отменить подписку, сбросить.
  - без `style` — навигация, справка, второстепенное.

  Если билдер `InlineKeyboard` в текущей версии grammY не принимает `style` — собери кнопку объектом вручную и передай в `reply_markup: { inline_keyboard: [...] }`. Не отказывайся от цвета из-за билдера.
- **Иконки — единый монохромный набор.** Либо кастомные эмодзи через `icon_custom_emoji_id` (работает только если у владельца бота есть Telegram Premium или юзернейм с Fragment), либо строгие юникод-символы. Разноцветные эмодзи вразнобой (🔥💎🚀) убивают ощущение продукта.
- **«Назад» — всегда последней строкой, отдельным рядом, всегда с одной иконкой.** На корневом экране «Назад» нет.
- Список сумм/тарифов — по одной кнопке в ряд, по возрастанию.
- Внешняя ссылка (`url`) — в самом низу, перед «Назад»: она уводит из бота. Значок `↗` у `url` и квадратик у `web_app` клиент рисует сам — не дублируй эмодзи в тексте кнопки.

## Тон

- На «ты». Глаголы вместо отглагольных существительных.
- Тире как основной знак ритма, двоеточия редко. Короткая строка.
- Ноль канцелярита: «вы можете воспользоваться», «данный функционал», «в целях», «осуществляется».
- Ноль извинений и восторгов. Не «Упс! Что-то пошло не так 😔», а «Не получилось создать кадр. Баланс не списан — попробуй ещё раз».
- Ошибка говорит, **что делать дальше**, и снимает главный страх (деньги на месте).
- Пустое состояние — не «Список пуст», а приглашение к первому действию.

## Эталон (чужой пример, возьми за основу то, что уже есть в боте)

```html
✋ Привет, {name}!
Добро пожаловать в <b>AI Persona</b> — здесь нейросеть рисует, оживляет и общается.

🎨 <b>Создать изображение</b>
Пришли своё фото и выбери образ — или опиши кадр словами, нарисуем с нуля.

🎥 <b>Создать видео</b>

```

# i18n

- **Никакого текста в коде.** Каждая строка живёт в `locales/`, в коде только ключ.
- Ключи по экранам: `payment.stars.title`, `payment.stars.button.back`. Плоские неймспейсы вида `text_1` запрещены.
- **Лимит в 30 символов на кнопку проверяется по самому длинному языку**, не по русскому. Немецкий и английский длиннее — если лейбл переносится хоть в одной локали, укорачивай во всех.
- Плюрализация через возможности плагина, не через `if (n === 1)`.
- Числа, валюты и даты форматируются по локали, а не конкатенацией.
- Добавляешь строку — добавляй **во все локали** сразу. Отсутствующий ключ не должен фолбэчиться молча.

# Definition of Done

Задача не закончена, пока не пройдено:

- [ ] `typecheck` и `lint` зелёные
- [ ] Каждый новый экран отрисовывается целиком из состояния, без «дописать сверху»
- [ ] Есть мостик `⌄` к клавиатуре
- [ ] Ключевой факт (курс/цена/баланс) виден, если экран про деньги
- [ ] Оффер продублирован, если экран внутри воронки оплаты
- [ ] Ровно одно главное действие, и оно `primary` или `success`
- [ ] Кнопок ≤ 8, лейблы ≤ 30 символов в самой длинной локали
- [ ] «Назад» есть везде кроме корня, иконка та же самая
- [ ] `callback_data` латиницей и ≤ 64 байт (проверь самый длинный)
- [ ] `answerCallbackQuery` вызывается на каждой ветке
- [ ] Есть состояние загрузки и внятный текст ошибки
- [ ] Текстовый и медийный режим не смешаны внутри одного потока
- [ ] Все новые строки добавлены во все локали

# Не делай

- Не отправляй новое сообщение там, где можно отредактировать текущее.
- Не оставляй нажатие без визуального отклика.
- Не показывай `Error 500` — пиши, что делать и что деньги на месте.
- Не вставляй markdown (`###`, `**`, `- `) в текст сообщения.
- Не ставь больше двух `primary` на экран — иерархия схлопывается.
- Не прячь цену: стоимость видна **до** нажатия, а не после.
- Не делай экран, единственная кнопка которого — «Назад». Это тупик: верни данные туда, откуда пришёл юзер.
- Не переспрашивай подтверждение у безобидных действий. Подтверждение — только для необратимого и платного.
- Не хардкодь тексты, даже «временно».
- Не добавляй зависимость, если задачу решают 20 строк.

# Когда сомневаешься

- **Глубина > 3 нажатий до целевого действия** — перепроектируй поток, а не оправдывай его.
- Если задача допускает больше одного прочтения — задай **один** уточняющий вопрос перед тем, как писать код. Не список вопросов.
- Прежде чем писать экраны — покажи карту переходов списком `экран → кнопки → куда ведут`. Тексты пиши после того, как карта согласована.
